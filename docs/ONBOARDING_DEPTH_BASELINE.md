## Current contract and depth limit

The [onboarding design](ONBOARDING_V2.md) calls for a few evidence-labeled end-to-end flows with entry, decisions, persistence, side effects, and visible gaps. The [Debtbox fixture](ONBOARDING_V2_DEBTBOX_FIXTURE.md) is an illustrative target, not observed CLI output. Current code builds a repository-only guide from static findings, marks sections for safe regeneration, detects Nest routes/module relationships, and can explain two specially shaped traces ([guide orchestration](../packages/cli/src/generate-onboarding-guide.ts), [trace scanner](../packages/scanners/src/route-traces.ts), [explanation rules](../packages/standards/src/explained-flow.ts), [renderer](../packages/renderers/src/onboarding-guide.ts)). It labels runtime claims unverified and preserves explicit unknowns. The scanner enters exactly one directly called injected service method from a route; its method inspection records certain guards, `status/state/action` assignments, injected repository calls, selected service calls, and gaps. It does not continue through local helpers or into called methods, recognize a local `queryRunner.manager` alias as persistence, or model transaction boundaries. The explainer currently requires a narrow unconditional awaited repository `save` pattern or a specific two-status-branch pattern. The renderer selects at most three candidates and at most two explanations.

## Diagnosis and next tracing spike

- **Scanner defects/limits:** Local receiver aliases and transaction manager calls disappear (`queryRunner` in Madar); local helpers and injected call bodies stop at their call sites (Debtbox fee snapshot, payment group lookup, Sanad generation). A bounded, evidence-bearing continuation should distinguish resolved source calls from external/library calls and stop on unsupported edges.
- **Insufficient evidence:** The plain Node fixture has no source, the Nest fixture has empty handlers, and no static scan proves runtime state, delivery, rollback, or recovery. These are explicit unknowns, not missing runtime conclusions.
- **Selection defects:** Madar's three highest-scoring candidates have zero explanations; Debtbox payment initiation is left as a candidate despite substantive source, while the guide cannot connect it to the scheduled payout path (`src/module/payment/payout-scheduler.service.ts:20`). Ranking favors route names and local operation counts rather than demonstrated learning depth ([selection](../packages/renderers/src/onboarding-guide.ts)).
- **Rendering defects:** Madar's root-import line lists roughly a hundred modules, obscuring entry points. Candidate rows disclose a direct method but neither the scanner's partial guard/read evidence nor the first unresolved edge. The `Debtbox` guide is stronger: its steps and uncertainty labels are sufficient for locating creation/consent guards, ordered saves, and attempted side effects; deeper tracing would improve the fee helper, consent-to-Sanad path, payment checkout and later payout, not invalidate those direct-call claims.

Acceptance examples for the next spike (static claims only):

1. **Neutral fixture:** Extend `OrderController.create` → `OrderService.create` in `packages/scanners/src/route-traces.test.ts:16-40` with a same-file helper or a second injected service method containing a visible guard/call. The guide should cite the continuation and its stop edge, while still labeling the existing indirect and dynamic calls at `:25-27` unresolved.
2. **Madar transaction:** `MobileFleetController.assignDriverToTruck` → `MobileFleetService.assignDriverToTruck` (`src/module/fleet/controllers/mobile-fleet.controller.ts:125-130`; `src/module/fleet/services/mobile-fleet.service.ts:585-690`) should expose the five initial reads/guards, three conditional manager saves, and commit/rollback/release branches with source references. It must not assert that any branch ran or that rollback succeeded.
3. **Debtbox creation:** `DebtService.addDebt` (`src/module/debt/debt.service.ts:100,155-199,208-228`) should continue through `applyExpectedFeeSnapshot` with bounded depth, preserve the separate save and caught push distinctions, and leave external delivery unresolved.
4. **Debtbox payment:** `PaymentService.initiatePayment` (`src/module/payment/payment.service.ts:65,82,103-179`) should show the early return versus checkout creation branches and the HyperPay call after recorded transaction data; payout remains a separate scheduled entry until a supported code link is established.

No newcomer validation was performed.

## Focused symbol-aware tracing spike (2026-09-30)

The isolated [prototype](../experiments/onboarding-trace-spike.mjs) uses the installed TypeScript 5.9.3 compiler API and the target repository's `tsconfig.json` options. It creates a `Program` rooted at the requested controller file, follows imports, and uses `TypeChecker` method symbols. It does not feed guide generation. The [neutral Nest fixture](../experiments/fixtures/nest-trace/controller.ts) and [focused tests](../experiments/onboarding-trace-spike.test.mjs) cover a route call, same-class helper, cross-file injected providers, exclusive `if/else` branches, a catch, status assignments, a dynamic call, an interface-typed provider, and an unsupported project function. Each followed edge contains a call-site `file:line` and the declared target's symbol and `file:line`. “Declared target” means a statically selected declaration, not a guarantee of runtime dispatch.

### Madar before and after

**Before:** the generated guide stops at `POST /v0.0.1/api/mobile-fleet/assign-driver-to-truck` → `MobileFleetController.assignDriverToTruck` → `MobileFleetService.assignDriverToTruck` (`src/module/fleet/controllers/mobile-fleet.controller.ts:114,130`; `src/module/fleet/services/mobile-fleet.service.ts:585`). It offers no explained steps.

**Prototype, cited static path:**

1. The handler's call at `mobile-fleet.controller.ts:130` resolves to `MobileFleetService.assignDriverToTruck` at `mobile-fleet.service.ts:585`. Constructor injection itself creates no call edge.
2. The service calls declared `FleetRepository.getFleetById` (`mobile-fleet.service.ts:602` → `src/module/data/repository/fleet.repository.ts:698`), `TruckRepository.getTruckById` (`:607` → `truck.repository.ts:569`), and `DriverRepository.getDriverById` (`:612` → `driver.repository.ts:77`). Each call is followed by a visible missing-record/ownership throw branch at `:603-615`.
3. It calls declared `ShipmentRepository.getRunningShipmentByTruckId` (`:618` → `shipment.repository.ts:13337`) and `getRunningShipmentByDriverId` (`:624` → `shipment.repository.ts:13378`), with separate throw branches at `:619-626`. Those repository methods call same-class plural helpers at `shipment.repository.ts:13339,13380`; the depth-two prototype cites those edges but does not follow them further.
4. Under `driver.truck && driver.truck.id !== truckId` (`mobile-fleet.service.ts:630`), it checks the former truck's shipment at `:632`, may throw at `:633-639`, sets `driver.truck = null` at `:643`, and calls `queryRunner.manager.save(driver)` at `:644`. The second branch (`:648-667`) checks the truck's previous driver and may clear/save it. A third branch (`:670-673`) may assign/save the requested truck. The conditions are kept separate; the prototype does not claim all branches execute.
5. Calls to `queryRunner.commitTransaction`, `rollbackTransaction`, and `release` appear at `:675,683,690`; the latter two are in catch/finally. These are cited calls, not proof of a committed or rolled-back outcome.

**First remaining gap:** `this.dataSource.createQueryRunner()` at `mobile-fleet.service.ts:597` has no source method body in the dependency-free snapshot. The subsequent `queryRunner` receiver is a local alias, so `connect`, `startTransaction`, the three `manager.save` calls, commit, rollback, and release remain unresolved method targets. The prototype labels each `save` a **write-like call with unresolved target**; it does not claim a database write occurred. `FleetRepository.getFleetById` and two other repository reads place their query bodies inside `new Promise(async ...)` callbacks (`fleet.repository.ts:699`, `truck.repository.ts:570`, `driver.repository.ts:78`), which this bounded prototype explicitly leaves untraced.

### Debtbox comparison and precision

The existing guide already explains `DebtController.addDebt` → `DebtService.addDebt` (`src/module/debt/debt.controller.ts:48`; `src/module/debt/debt.service.ts:100`). The prototype also resolves `DebtService.validateDebtCreationAmount` (`debt.service.ts:102` → `:242`) and its three throw guards (`:243-250`), plus the previously untraced `DebtService.applyExpectedFeeSnapshot` (`:155` → `:254`) and its fee-field assignments (`:256-264`). It resolves the nested notification-language call at `:213` to `NotificationService.resolveNotificationLanguage` (`src/module/notification/notification.service.ts:95`) and labels it a nested argument, without inventing call order. Existing direct observations remain: awaited save call sites at `debt.service.ts:156,178,199` and a conditional Firebase attempt at `:215`; their outcomes stay unverified. The first unresolved edge on the fee-helper continuation is `computeExpectedDebtFeeSnapshot` at `:255` (project free function outside this prototype's method-call scope); the first unresolved save target on the main path is inherited `DebtRepository.save` at `:156` because TypeORM is absent.

No false method-call edge from a module import or constructor injection appeared in the neutral fixture or either repository trace. Precision limits still matter: a TypeScript method symbol identifies a *declared* target, not necessarily a runtime override; a repository `get*` or `save` name is only a read-like/write-like call, not proof of I/O; nested argument calls must not be flattened into separate sequential steps. The prototype marks dynamic `this.notifications[method]` and interface-typed `Dispatcher.send` unresolved in the fixture, and stops at unsupported project free functions, callbacks, aliases, and depth limits. Its branch labels preserve `when`, `else`, `catch`, and `finally` rather than joining mutually exclusive paths.

These are separate single-process runs on the same machine and snapshots; the trace is **additional work**, not a faster replacement for guide generation. A preceding route-scoped Madar run took 2.514 s and 554.1 MiB, indicating memory variability. Loading all tsconfig files instead took 3.872 s and 723.9 MiB in one Madar run. The full Madar import graph remains sizable even with one route as the root.

**Recommendation: narrow scope before integration.** The TypeScript compiler API suffices for this spike: it resolved the cross-file edges and explicit limits without another dependency. `ts-morph` is already used by the current scanner, but its wrapper is not justified for this isolated technique; no dependency was added. A production follow-up should first constrain tracing to selected routes, bound method depth and fan-out, carry branch context and call-site/target evidence, and render unresolved aliases and external methods plainly. Do not merge this prototype into `tk onboard guide` until those precision rules and the memory cost are evaluated against more routes.
